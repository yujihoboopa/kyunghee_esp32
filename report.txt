탐구 주제: Lua 가비지 컬렉션이 ESP32 실시간 작업의 지연시간에 미치는 영향

1. 탐구 동기와 목적

1학년 학술제에서 ESP32에서 C/C++ 이외의 언어로 프로그래밍하는 방법을 탐구했다. 언어 기능을 직접 구현하는 과정에서 기능 추가에 따른 오류와 실행 속도 문제를 경험했고, 임베디드 환경을 위해 이미 사용되는 Lua를 ESP32에서 실제로 활용할 수 있는지 알아보기로 했다. Lua를 쓰면 개발이 간결해질 수 있지만, 동적 메모리 관리가 실행시간과 메모리 안정성에 미치는 영향을 확인해야 한다.

이번 탐구는 ESP32-WROOM-32 DevKitC에서 Lua 5.1.5를 실행하고, GC가 메모리 회수뿐 아니라 주기 태스크와 BLE 알림 송신에 미치는 영향을 측정하는 것을 목표로 한다. 객체 종류와 참조 구조, GC 설정 및 내부 단계, FreeRTOS 태스크 지연, BLE 송신을 분석한다. GC 실행시간과 태스크 지연, BLE 요청/실제 수신 지연은 서로 다른 값이므로 별도로 기록한다.

2. 이론적 배경

프로그램은 실행 중 필요한 크기의 메모리를 동적으로 할당할 수 있다. 수동 메모리 관리에서는 더 이상 쓰지 않는 메모리를 개발자가 해제해야 하며, 해제를 놓치면 메모리 누수가 생길 수 있다. Lua는 가비지 컬렉터가 Lua 객체의 참조 가능성을 추적하고 더 이상 도달할 수 없는 객체를 회수한다. 따라서 객체 수명 관리가 편리해지는 반면, GC가 수행되는 동안 CPU 시간과 메모리 대역폭을 사용한다.

클로저와 테이블 같은 Lua 객체는 함수가 반환된 뒤에도 참조될 수 있어 단순한 함수 스택 공간만으로 수명을 관리할 수 없다. Lua는 자체 메모리 할당 인터페이스(lua_Alloc)와 GC를 사용한다. 이 실험의 allocator는 ESP-IDF의 내부 8-bit heap에서 메모리를 할당하며, 이는 운영체제에 메모리를 요청하는 방식이 아니다. 또한 C 스택에서 참조되는 Lua 객체는 GC root가 될 수 있으므로, 생성 후 참조를 제거했다는 사실만으로 수집 완료를 판단하지 않고 회수 전후 메모리와 실제 GC 동작을 함께 확인해야 한다.

대상 Lua 5.1.5는 증분형 GC와 pause/step multiplier 설정을 사용한다. Lua 5.4의 generational GC 및 전용 설정은 이번 대상에 적용하지 않는다. GC 내부 시간은 esp_timer_get_time()으로 계측한다. 계측 함수 호출과 정적 배열 기록도 작은 측정 오버헤드를 추가한다.

3. 실험 환경 및 구현

하드웨어: ESP32-WROOM-32 DevKitC (사용자 제공 환경)
개발 환경: ESP-IDF 프로젝트, 타깃 esp32
프로그램: C, Lua 5.1.5
RTOS: FreeRTOS
BLE: ESP-IDF NimBLE GATT Peripheral
시간 측정: esp_timer_get_time() 마이크로초 단위
메모리 측정: Lua 사용자 정의 allocator, ESP-IDF 내부 SRAM heap
기록: UART CSV형 로그, 추후 호스트에서 파일 저장

프로젝트는 components/lua51에 포함된 Lua 소스를 빌드하며 lgc.c singlestep 및 luaC_step에 계측 코드를 포함한다. BLE 광고 이름은 LuaGC-ESP32이며, 연결된 Central이 실험용 Notify characteristic을 구독하면 주기적인 센서 시퀀스 메시지를 받을 수 있다. Lua 태스크는 Core 1에 고정되어 100 ms마다 Lua 함수를 실행하고 테이블을 갱신한다. 임시 중첩 테이블을 할당하고 20번째 호출마다 collectgarbage('collect')로 전체 GC를 요청한다. 별도 측정 태스크도 Core 1에서 10 ms 주기로 깨어나 예정 시각과 실제 시각의 차이를 출력한다. BLE 송신 태스크는 Core 0에서 큐를 받아 알림 제출을 시도한다.

빌드 확인: idf.py build 성공. 실행 환경에서 idf.py --version은 ESP-IDF v6.1-dev-6443-g8bf9c476cfa를 보고했다. 생성된 펌웨어는 build/kyunghee_esp32.bin이다. 펌웨어 빌드 성공은 보드 플래시 및 실제 동작 검증과 구분한다.

4. 실험 설계

실험 1: 객체 종류 및 참조 구조
단순/중첩 테이블, 클로저와 upvalue, weak table, __gc finalizer, full userdata, C API 스택 root 조건을 구성한다. 객체 개수와 크기를 맞추고 각 조건에서 살아 있는 참조를 유지하거나 제거한 뒤 GC를 수행한다. GC 전후 allocator 사용량, 생성 수, 수집 여부 및 실행시간을 기록한다.

실험 2: GC 제어 설정
기본 자동 GC, GC 중지 후 객체 생성 및 강제 전체 수집, 재시작 후 자동 수집, collectgarbage('step') 반복 호출을 비교한다. Lua 5.1.5에서 지원하는 pause와 step multiplier를 사용하며 Lua 5.4 전용 설정을 적용하지 않는다. GC 빈도, 누적/최대 실행시간, 전후 메모리 및 회수량을 기록한다.

실험 3: GC 내부 단계
lgc.c의 GC 상태 전이 및 singlestep을 계측해 pause, mark/propagate, atomic, 문자열 sweep, 객체 sweep, finalize, 전체 step 시간을 기록한다. 단계별 실행시간과 호출 횟수를 비교한다.

실험 4: FreeRTOS 지연
주기 측정 태스크와 Lua GC 부하를 같이 실행한다. 계획된 조건은 두 태스크가 같은 코어에서 실행되는 경우와 서로 다른 코어에서 실행되는 경우, 코어 0/1 배치를 바꾼 경우이다. 예정 시각과 실제 태스크 시작 시각의 차이를 계산한다. 평균, 중앙값, P95 및 최댓값을 조건별로 비교한다.

실험 5: BLE 송신 지연
NimBLE Peripheral에서 일정 주기로 Notification을 요청하고 GC 부하를 없음/낮음/높음/강제 전체 GC로 바꾼다. 송신 요청, 송신 태스크 처리 및 BLE API 제출 시각을 기록한다. Central 장치에서 시퀀스 번호와 실제 수신 시각을 기록하고 패킷 간격 및 손실을 구한다. Central 수신 지연에는 연결 간격과 무선 환경도 포함되므로 태스크 지연과 분리해 해석한다.

실험 6: 통합 부하
Lua에서 센서 데이터를 만들고 테이블/문자열로 처리하면서 주기적 BLE 송신을 수행한다. GC 단계시간, allocator 사용량, 태스크 지연, BLE 요청/수신 시각 및 손실을 함께 분석한다.

각 조건은 최소 30회 반복하고 평균, 중앙값, P95, 최댓값을 계산한다. 실제 실험에서는 보드, 전원, BLE 연결 간격, 전송 주기/크기, 태스크 우선순위와 코어 배치를 고정하고 조건별로 기록한다. UART 로그 출력이 스케줄러와 UART에 부하를 더할 수 있으므로 출력 빈도도 통제해야 한다.

5. 측정 데이터 해석 방법

태스크 지연: L_task = 실제 태스크 시작 시각 - 예정 태스크 시작 시각
BLE 수신 지연: L_BLE = Central 수신 시각 - ESP32 송신 요청 시각
GC 실행시간: 계측 구간의 종료 시각 - 시작 시각
메모리 회수량: GC 직전 allocator 추적 사용량 - GC 후 추적 사용량

Lua allocator 추적량은 Lua가 allocator에 요청한 블록의 총량이며 ESP32 전체 자유 heap 또는 실제 물리 메모리 단편화와 동일하지 않다. NimBLE notify API의 반환은 무선 전송 완료를 뜻하지 않으므로 Central 수신 로그가 있어야 실제 BLE 지연을 산출할 수 있다.

6. 실행 및 측정 결과

수정 펌웨어를 ESP32에 실행하고 2026-11-15 UART monitor 캡처를 약 405초 수집했다. UART 원본은 results/uart-capture.log, 파싱 이벤트는 results/uart-events.csv, 요약은 results/esp32_lua_gc_results.csv에 저장했다. BLE Central 원본 및 프로파일별 요약은 results/ble-central.csv와 results/ble-central-summary.csv이다. 파싱은 tools/parse_uart_capture.py로 재현할 수 있다. 로그에서 Lua 초기화와 객체군 실험이 완료됐고 12개 프로파일을 세 차례 이상 순환했으며, 이번 실행에서는 stack overflow 메시지가 없었다. 캡처 끝에는 다음 프로파일 실행이 시작된 상태라 마지막 반복은 완결되지 않았다.

### 6-1. 객체 종류별 강제 GC 결과

아래 값은 부팅 한 번에서 각 조건을 30회 반복한 평균이다. GC 시간의 P95와 최댓값은 30개 표본에서 계산했다. 할당/회수량은 allocator 추적량이며, 일부 조건은 참조를 의도적으로 유지했다.

| 객체 조건 | 할당 평균 (B) | 회수 평균 (B) | GC 평균 (us) | GC P95 (us) | GC 최댓값 (us) | 생존/후처리 관측 |
|---|---:|---:|---:|---:|---:|---|
| 단순 테이블 | 2,080 | 2,280 | 2,392 | 2,442 | 2,461 | 확인 함수 없음 |
| 중첩 테이블 | 14,368 | 14,388 | 4,975 | 5,015 | 5,043 | 확인 함수 없음 |
| 클로저/upvalue | 7,456 | 7,474 | 3,798 | 3,844 | 3,893 | 유지한 클로저 1개 확인 |
| weak-value 테이블 | 6,752 | 6,720 | 3,687 | 3,724 | 3,733 | weak value 잔존 0개 |
| 일반 full userdata | 4,608 | 4,648 | 3,074 | 3,115 | 3,148 | 별도 생존 확인 없음 |
| `__gc` userdata | 4,608 | 20 | 2,947 | 2,983 | 2,988 | GC마다 평균 96개 finalizer 콜백 관측 |
| C API 스택 root | 측정 안 함 | 측정 안 함 | 12,204 | 12,347 | 12,539 | 스택에 둔 root 테이블 1개 생존 |

객체 조건마다 할당량이 달라 완전히 동등한 작업량 비교는 아니다. 중첩 테이블은 단순 테이블보다 할당량과 GC 시간이 컸다. weak value는 회수 후 참조 검사에서 남지 않았고, C API 스택에 유지한 테이블은 생존했다. finalizer 조건의 96은 생존 객체 수가 아니라 trial당 실행된 finalizer 콜백 수의 평균이다. C API root 시간에는 128개 임시 테이블 생성과 전체 GC가 포함되며 allocator 변화는 계측하지 않아 다른 행과 직접 비교하기 어렵다.

### 6-2. GC 단계 및 설정별 결과

GC 내부 계측은 각 상태 단계 이벤트의 횟수, 누적 시간, 평균 시간, 최대 단일 이벤트 시간을 RAM에 누적해 출력했다. 세 번 이상 반복된 부하 프로파일의 집계 결과 중 고부하 설정 비교는 다음과 같다. P95는 요약 로그에 남지 않아 산출하지 않았다.

| 설정 | step 호출 수 | step 평균 (us) | step 최댓값 (us) | atomic 평균/최댓값 (us) | sweep 평균/최댓값 (us) |
|---|---:|---:|---:|---:|---:|
| 기본 고부하 | 2,476 | 499.2 | 2,782 | 271.1 / 305 | 328.1 / 632 |
| pause=100 | 8,492 | 223.8 | 2,749 | 193.8 / 293 | 161.4 / 603 |
| stepmul=400 | 1,539 | 839.2 | 5,677 | 120.4 / 198 | 314.7 / 996 |
| 20회마다 강제 전체 GC | 2,487 | 483.4 | 2,757 | 190.1 / 290 | 299.6 / 593 |

pause=100 조건은 기본 고부하보다 step 이벤트가 많고 평균 step 시간은 짧았다. stepmul=400은 호출 수가 적은 대신 평균 및 최댓값이 가장 컸다. 이는 GC 파라미터가 회수 총량보다 작업 분할과 개별 step 지연에 영향을 준다는 관측과 일치한다. 다만 프로파일별 heap 상태와 할당 이력이 같도록 완전히 통제한 반복 실험은 아니므로 설정만의 인과 효과로 일반화하지 않는다. `mark`와 문자열 sweep은 이벤트 평균이 약 0.8–1.3 us로 타이머 해상도와 계측 오버헤드에 가까워 단계별 정밀 비교에 한계가 있다.

### 6-3. FreeRTOS 지연 및 Lua 호출시간

각 프로파일에서 Lua 태스크의 20개 표본 창 요약을 결합했다. 표의 `창 P95 최댓값`은 모든 원시 표본을 합친 P95가 아니라 각 창의 P95 중 최댓값이다. 측정 태스크는 100개 표본 창으로 출력했다. 구현은 첫 표본의 지연을 offset으로 빼므로 값은 절대 deadline 지연이 아니라 프로파일 시작 표본 대비 상대 지연이다. 음수는 실제로 예정 시각보다 먼저 실행됐다는 뜻이 아니다.

| 프로파일 | Lua 태스크 상대 지연 평균 (us) | 창 P95 최댓값 (us) | 창 최댓값 중 최고 (us) | Lua 호출 평균 (us) | Lua 호출 최댓값 (us) |
|---|---:|---:|---:|---:|---:|
| 기준, 같은 코어 0 | 45.4 | 699 | 2,315 | 1,233 | 3,141 |
| 기준, 같은 코어 1 | 21.6 | 318 | 403 | 844 | 1,076 |
| 기준, Lua 0 / 측정 1 | 2.4 | 13 | 13 | 1,346 | 2,810 |
| 기준, Lua 1 / 측정 0 | -0.4 | 4 | 6 | 840 | 945 |
| 자동 GC, 같은 코어 0 | 32.8 | 686 | 981 | 14,794 | 27,641 |
| 자동 GC, 같은 코어 1 | 13.9 | 430 | 467 | 13,122 | 21,754 |
| 자동 GC, Lua 0 / 측정 1 | 33.1 | 680 | 925 | 14,530 | 26,334 |
| 자동 GC, Lua 1 / 측정 0 | -0.3 | 0 | 1 | 12,940 | 21,843 |
| 고부하 기본 설정 | 44.0 | 430 | 596 | 26,531 | 38,994 |
| 고부하 pause=100 | 39.6 | 405 | 493 | 24,480 | 39,645 |
| 고부하 stepmul=400 | 27.9 | 417 | 499 | 24,113 | 37,144 |
| 고부하 강제 전체 GC | 41.3 | 411 | 508 | 25,550 | 40,892 |

Lua 호출시간은 GC만의 시간이 아니라 Lua 코드 실행, 테이블 할당, GC 작업이 합쳐진 값이다. 객체 부하가 커진 조건에서 호출시간이 증가했고, 강제 전체 GC 조건의 단일 호출 최댓값은 40.892 ms였다. 반면 요약 창의 태스크 상대 지연은 조건별로 일관된 증가를 보이지 않았다. 실제 스케줄링 지연을 절대값으로 비교하려면 offset 보정 없이 공통 기준 시각으로 재측정해야 한다. 별도 probe의 일부 baseline 창에는 큰 편차가 있어 (최대 11.149 ms), 본문에서는 원시 probe 분포를 GC 효과의 결론 근거로 사용하지 않았다.

### 6-4. 메모리 및 BLE 결과

Lua allocator는 200개 체크포인트에서 현재 추적량 31,496–121,736 B, peak 49,931–160,072 B를 기록했고 할당 실패는 0회였다. 이는 Lua allocator가 관리하는 블록 추적치로 ESP32 전체 heap 여유량을 뜻하지 않는다.

UART 로그의 BLE 송신 요약은 총 4,000개 요청 처리, NimBLE notify 제출 성공 3,899건, 실패 101건이다. 실패는 Central 연결/구독이 없던 시작 구간 및 연결 전환 구간에 누적됐고, 이후 요약에서 실패 수가 더 증가하지 않았다. Central 캡처에는 3,942개 알림이 기록됐으며 12개 프로파일 각각 100개의 고유 시퀀스 번호와 집계 기준 내부 공백 0건이 확인됐다. 반복 프로파일에서 시퀀스 번호가 재사용되므로 이 결과는 각 실행 회차의 패킷 손실률을 입증하지는 않는다.

Central 시각 보정으로 계산한 추정 단방향 수신 지연은 평균 31.018 ms, 중앙값 31.259 ms, P95 51.439 ms, 범위 5.892–89.168 ms였다. ESP32와 Central 간 오프셋 불확실성은 44.601 ms로 지연 추정치와 비슷하거나 더 크다. 따라서 절대 단방향 지연과 프로파일별 차이는 정밀한 수치 결론으로 해석하지 않고 참고값으로만 제시한다. UART 캡처는 약 405.6초 지점에서 끝나며 Central 기록은 ESP 타이머 약 408.0초까지 있어 두 파일의 종료 구간이 완전히 일치하지 않는다.

7. 구현 범위와 측정 한계

최신 실행에서 초기화와 객체 실험을 전용 16 KB 스택 setup task에서 완료했고 405초 UART 기록에 stack overflow가 없었다. 따라서 이전 `main` task stack overflow는 이번 실행에서는 재현되지 않았다. 네 가지 baseline 프로파일은 각각 4회 완료했고, 나머지 GC 프로파일은 각각 3회 완료했다. 캡처 종료 시 다음 회차의 `auto_gc_same_core0`가 일부 진행 중이었다. 객체군 실험은 조건당 30회지만 모두 한 번의 부팅에서 수행했다. 계획한 “조건별 최소 30회 독립 반복”을 만족하지 않으므로 결과는 단일 보드·단일 부팅의 탐색 실험이다.

UART에는 BLE Notify마다 NimBLE info 로그도 함께 기록됐다. 이 출력은 태스크 및 UART 부하를 추가할 수 있고, BLE 요약 시각과 GC/태스크 계측에도 영향을 줄 수 있다. 또한 주기 태스크 지연은 프로파일 첫 샘플 기준으로 offset 보정돼 절대 deadline 지연을 제공하지 않는다. GC 단계 요약은 평균과 최댓값만 제공하여 P95/분포를 복원할 수 없다. 단계 시간이 1 us 안팎인 `mark` 및 문자열 sweep은 esp_timer 해상도와 계측 비용에 가까워 정밀한 단계 순위 비교에 부적합하다.

8. 결론

이 실행에서 Lua 5.1.5는 ESP32-WROOM-32에서 초기 객체군 실험과 12개 부하 프로파일을 수행했고, 실행 중 main task stack overflow는 나타나지 않았다. 객체 구조에 따라 강제 GC 평균 시간은 단순 테이블 2.392 ms, 중첩 테이블 4.975 ms, 클로저/upvalue 3.798 ms, weak-value 테이블 3.687 ms, 일반 userdata 3.074 ms였다. 참조 확인 결과 weak value는 수집되고 명시적으로 유지한 closure 및 C API root는 생존했다.

고부하 Lua 호출은 평균 약 24–27 ms였고 최대 40.892 ms까지 관측됐다. GC 설정은 step 횟수와 step별 작업시간을 바꿨으며, pause=100은 더 많은 짧은 step, stepmul=400은 더 적은 긴 step을 보였다. BLE는 Central 연결 이후 알림이 수신됐으나 연결 초기의 제출 실패 101건이 있었고, 수신 로그의 시계 오차가 커 정밀한 one-way 지연 비교에는 부적합했다. 태스크 상대 지연은 설정 간 일정한 증가 패턴을 보이지 않았으며 절대 지연 계측으로 재실험할 필요가 있다.

따라서 이번 데이터는 객체 구조와 GC 설정에 따른 비용 차이 및 Lua 호출의 긴 실행 구간을 보여주는 탐색 결과다. GC가 FreeRTOS 또는 BLE 지연을 특정 크기만큼 증가시킨다고 단정할 수는 없다. 절대 deadline 기준의 태스크 계측, UART 로그 부하 제거, Central 시계 동기화 개선, 프로파일별 독립 반복을 적용하면 실시간 영향에 대한 더 강한 결론을 낼 수 있다.

9. 어려웠던 점 및 개선 방향

첫 실행에서는 상세 단계별 UART 출력이 태스크 실행을 방해하고 기록 버퍼도 넘쳤다. 이를 RAM 집계 방식으로 바꿔 해결했고, 이번 실행에서는 GC 단계 요약을 확보했다. 다음 개선은 Notify별 NimBLE info 로그를 낮추거나 끄고, 태스크와 BLE 타임스탬프를 하드웨어/공통 기준으로 동기화하며, 시퀀스 번호에 실행 회차 ID를 추가하는 것이다. 객체별 할당량을 같게 맞추고 각 조건을 여러 번 재부팅해 반복하면 조건 간 통계 비교의 신뢰도를 높일 수 있다.
